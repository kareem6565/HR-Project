# AI Contract Schema

This document describes the Phase 3.2 structured AI output contract package and
its schema-versioning boundary, including the Phase 4.1 structured job
requirement vocabulary and the Phase 4.2 structured per-requirement match
evidence contract. It is intentionally short: it does not rewrite the
architecture or product documentation.

## Location

- Package: `backend/app/ai/contracts/`
- Maps to the AI application layer described in `docs/architecture.md`.
- Contracts are plain Pydantic models: no SQLAlchemy, no database behavior, and
  no HR final decision fields.

## Schema Versioning

The initial contract schema version is `1.0`; Phase 4.1 added `1.1` for the
structured job requirement vocabulary, and Phase 4.2 added `1.2` for the
structured per-requirement match evidence contract.

- `AI_CONTRACT_SCHEMA_VERSION` is `1.1` and is the default for the job profile,
  candidate profile, and explanation contracts. Every contract carries a
  `schema_version` field that defaults to the current supported version, must be
  a non-empty string, and must be one of the supported versions
  (`SUPPORTED_SCHEMA_VERSIONS`, currently `{1.0, 1.1}`).
- `EVIDENCE_CONTRACT_SCHEMA_VERSION` is `1.2` and is the default for the match
  evidence contract (`MatchEvidenceListOutput`). It is versioned separately so
  that introducing the `requirement_ref`/`requirement_key` boundary does not
  re-point the other contracts.

This lets a producer signal which contract revision it conformed to and lets a
consumer reject unrecognized revisions before processing. `1.0` remains readable
everywhere; only the job profile contract gained a structured requirement
vocabulary in `1.1` and the match evidence contract gained a structured
per-requirement list in `1.2` (the other contracts simply inherit the new
default revision, which does not change their structure).

## Contracts

| Contract | Produced on | Structured fields |
| --- | --- | --- |
| `JobProfileExtractionOutput` | job profile extraction | `title`, `summary?`, `requirements[]` |
| `JobRequirement` | inside `JobProfileExtractionOutput.requirements` | `key`, `text`, `category`, `dimension` |
| `CandidateProfileExtractionOutput` | candidate profile extraction | `full_name`, `summary?`, `skills[]`, `experience[]` |
| `MatchEvidenceListOutput` | matching evidence | `evidence_items[]`, `provenance?`, `schema_version` |
| `MatchEvidenceOutput` | inside `MatchEvidenceListOutput.evidence_items` | `evidence_type` (`matched`/`missing`/`partial`), `requirement_ref` (mandatory, with `requirement_key`), `candidate_evidence?`, `strength?`, `provenance?` |
| `EvaluationExplanationOutput` | evaluation explanation | `summary`, `points[]` |

All contracts reject undeclared ("extra") fields.

## Job Requirements

`JobProfileExtractionOutput.requirements` accepts two shapes, never mixed in the
same list:

- **v1.0 flat shape**: `["Python", "PostgreSQL"]`. Read-only compatibility.
  Flat entries are normalized to canonical structured requirements with
  `category="important"` and `dimension="skill"` defaults applied at validation
  (and read) time.
- **v1.1 structured shape (canonical)**: list of `JobRequirement` objects with
  `text`, `category` (`must_have`/`important`/`nice_to_have`), and `dimension`
  (`skill`/`experience`/`education`/`responsibility`).

Rules:

- The LLM proposes only `text`, `category`, and `dimension`.
- `key` is always system-generated by `requirement_key()`:
  `"req-" + sha256(f"{category}\x00{normalized_text}")[:16]` where
  `normalized_text` strips and collapses whitespace. Any key present in the
  input is stripped and recomputed — an LLM-provided key is never trusted or
  persisted.
- `key` does not include `dimension`; duplicate keys are rejected (raised as a
  validation failure), and duplicates are detected on the normalized
  `text`/`category` pair. The same text in different categories yields distinct
  keys and is allowed.
- Newly extracted profiles are persisted canonically as v1.1 structured
  requirements with keys via `extracted.model_dump()`.
- `normalize_job_profile_requirements()` in `app/ai/contracts/validation.py` is
  the read-path helper: it maps either stored shape to canonical
  `JobRequirement` instances with system keys, so consumers (for example the
  candidate evaluation workflow) never depend on which shape a row was written
  in.

## Match Evidence

`MatchEvidenceListOutput` (schema v1.2) is produced by the evidence component of
the candidate evaluation workflow. It is a list shape:

- `evidence_items[]` is a list of `MatchEvidenceOutput` elements, one per job
  requirement.
- `provenance?` carries the workflow/provider/model/schema trace.
- `schema_version` defaults to `EVIDENCE_CONTRACT_SCHEMA_VERSION` (`1.2`).

Each `MatchEvidenceOutput` element:

- has a mandatory `requirement_ref` object that must carry a `requirement_key`
  matching the job requirement key format (see `is_requirement_key()`), and
- rejects duplicate `requirement_key` values within the list.

`validate_match_evidence_list(data, *, allowed_keys)` in
`app/ai/contracts/validation.py` further requires every returned
`requirement_key` to exist in `allowed_keys`, the exact requirement-key set
supplied to the producer. A key absent from that set (or a non-empty key set
when evidence is expected) fails validation with "not among the requirement
keys supplied to the AI". This ties each evidence element to an approved
requirement from the current job profile.

## Validation Boundary

Validation helpers in `app/ai/contracts/validation.py`:

- accept structured Python data,
- validate through Pydantic,
- return the validated contract, and
- translate Pydantic validation failures into the shared Phase 3.1
  `app.services.errors.ValidationError`.

They never persist anything and never call an external provider.

## Deliberately Undefined

The following are intentionally not specified because the repository does not
yet define enough information to safely finalize them:

- A nested candidate experience/skill entry model (experience is a flat list of
  strings).
- Match evidence `candidate_evidence` and `provenance` are free-form `dict`
  payloads mirroring the JSONB columns of the `MatchEvidence` model; their
  internal key vocabulary is not yet part of a contract. `requirement_ref` is
  now part of the v1.2 contract and requires a `requirement_key`.
- **Decisions and scores**: `MatchEvidenceOutput` is evidence only and
  `EvaluationExplanationOutput` is explanatory only. Neither contains a final
  score, an HR decision, a recommendation that implies a decision, or any
  authorization outcome. HR remains the final decision maker.
