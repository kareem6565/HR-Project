# HERA — Recruitment System Frontend (frontend_last)

React + Vite frontend for the Recruitment System. Talks to the FastAPI backend
through a service layer (`src/services/*.js`). There is **no mock data**: every
page renders real backend data or an honest empty/error state.

## Stack
- React 19 + Vite
- React Router v7 (routing, protected routes)
- Axios (API client, in `src/services/apiClient.js`)
- Recharts (dashboard charts)
- lucide-react (icons)
- oxlint (`npm run lint`)

## Getting started
```bash
npm install
npm run dev       # http://localhost:5173
npm run lint      # oxlint
npm run build     # production build -> dist/
npm run preview   # preview the production build
```

## Configuration (`.env`)
- `VITE_API_BASE_URL` — base URL including `/api/v1`. Default
  `https://soal.help/api/v1` (the repo's OpenAI-compatible Soal gateway /
  production FastAPI endpoint). For local work against the FastAPI backend set
  it to `http://localhost:8000/api/v1` (as an environment variable it overrides
  the `.env` value).
- `VITE_ORG_ID`, `VITE_USER_ID` — development identity defaults. The backend
  uses header-based identity (`X-Organization-Id` / `X-User-Id`); there is no
  login/JWT. The Development Identity page (`/identity`) persists overrides in
  localStorage; the `apiClient` sends the two identity headers on every request.

## AI provider (backend)
Screening/evidence/explanation generation runs through the backend's AI
provider. `backend/.env` currently sets `AI_PROVIDER=soal`,
`SOAL_BASE_URL=https://soal.help/api/v1`, `SOAL_MODEL=gemini-3.5-flash`, and
`SOAL_API_KEY` — the repo's OpenAI-compatible Soal gateway. With
`AI_PROVIDER=fake` (the default when unset) the backend uses the deterministic
`FakeAIProvider` instead. Scores are always computed by the backend
`ScoringService`, never by the frontend.

## What is wired to the backend
Everything. Service methods map 1:1 to the backend routes (`src/types/api/endpoints.js`),
including:
- Jobs CRUD + job-profile extraction/approval.
- `POST /jobs/{id}/screen` — batch CV screening (PDF/DOCX upload; candidate +
  resume + profile extraction + application + evaluation per file). Results
  panel links straight to each candidate's review.
- `GET /resumes/{id}/download` — CV download (binary attachment).
- Review workspace `GET /job-applications/{id}/review-bundle`, run evaluation,
  record HR decision (`advance`/`hold`/`reject`), which mirrors into the
  application pipeline status.
- `GET /talent-pool` — org-wide hold/advanced candidates ranked by score.
- HERA Assistant — real conversational chat (`POST /chat/threads` plus
  send-message endpoint). Runs the HERA assistant workflow (plan -> authorized
  tools -> compose) against real pipeline data, persisted as org-scoped threads.
- Interviews — `GET /interviews`, schedule / cancel / feedback submission, and
  `GET /interviewers` (org users) for interviewer selection.
- Interview Questions — curated banks plus candidate-specific questions
  generated by the backend from the candidate's real profile skills and
  requirement gaps (`GET /interview-questions?candidate_id=...`).
- AI Activity — `GET /ai-activity/runs`, `GET /ai-activity/stats` (last-24h
  counts/latency), and `POST /ai-activity/runs/{id}/retry` for failed runs.
- Evaluations, observability traces (`GET /workflow-runs/{id}`,
  `GET /ai-traces/{id}`), and AI settings.

## Screening flow (the key surface)
Upload CVs against a job → the backend returns a real 0–100 score, per
requirement evidence, an explanation, and extracted profile details (email,
phone, location, LinkedIn/GitHub/portfolio, skills, education, languages,
certifications). Scores come only from the backend `ScoringService`; the
frontend never computes them. The review page renders all of it and records the
final HR decision.

## Notes
- `frontend_last` is the canonical active frontend; the previous
  `frontend/frontend3/sandbox` iteration was retired at the release checkpoint.
- Every original feature (including interviews, interview questions, AI
  activity, and the chat/matching flow) is implemented against real backend
  endpoints with zero mock data; the frontend only maps wire formats
  (snake_case / lowercase statuses) to display form.
